# 0026: maps

Status: accepted, 2026-09-29.

## Context

Phase 9: maps, offline, and what is on the road between places. The pack already carries each
place's `at`, a point on the earth, and `map.open` hands a place to a map app. Neither of those
answers the question the brief asks, which is where today's places are in relation to each other,
and where in a terminal the gate is, both with no network and no tile server.

## Decision

**No tiles, and nothing fetched.** An offline map here is drawn from the pack's own numbers. Two
kinds, and the pack writes the second one itself:

- **the day's chart**: today's places as pins on plain paper, joined in the order the day visits
  them. The engine projects; nothing is downloaded.
- **a place's plan**: named pins in the picture's own coordinates, with an optional picture the
  pack ships. That is the terminal map: the gate, the platform, the lockers.

**The engine projects, the host draws.** `places` exposes `chart`: `{points, path, span_m}`.
`points` are the day's places that have an `at`, each `{id, name, x, y, state}` with `x` and `y`
in 0 to 1 and `y` down, fitted into the box with a tenth of a margin and one scale for both axes,
so the shape is not stretched. `path` is the same places in visit order, so a place visited twice
is one pin and two stops. `span_m` is the diagonal of what is drawn, for a scale line. A single
place, or several at one point, sits in the middle. With no place that has an `at`, `chart` is
null and the screen simply has no map.

The projection is equirectangular with a `cos` correction at the middle latitude: right for a day
you can walk or drive across, and honest about being nothing more.

**The device is not a pin.** `screen` never receives the device's coordinates, only which regions
it is inside ([decision 0020](0020-location.md)). A pin is marked `here` when the device is in that
place's region and `now` when it is the current block's place. Nothing else is inferred.

**A place's `plan` is data, canonical like the rest.** `{caption, image, points: [{name, x, y,
kind}]}`, the points in the picture's own 0 to 1 coordinates. `image` is a pack-relative path, read
by the host the way a document's `file` is, and a plan without one draws its pins on plain paper.
The example pack ships no picture: the terminal is pins and names, which is the whole point.

**`road`: what is between two places.** A moving block may carry `road`, a list of `{at, name,
what}`: the village the train passes, the stretch with no fuel, the viewpoint worth the stop. The
travel template lists it under the block's own answer. It is content, so the engine only checks
its shape.

**One new component, `Map`.** `points`, `path`, `image`, `caption` and `span`, the last drawn as a
scale line. One component for both kinds of map, because both are pins at their fractions of a
drawing. It labels its own pins, so a screen showing a chart needs no list beside it. Sixteen
components; the set still grows only by shell release
([decision 0005](0005-screens-compose-components.md)).

## Consequences

- `places` gains `chart`, one more known root for expressions. The tree version does not change.
- The validator learns `plan` (coordinates in range, a picture that stays inside the pack folder)
  and `road` (a list of mappings, `at` a time when present).
- The travel template gains a `chart` screen off the agenda and the moment, draws `place.plan`
  on a moment whose place has one, and lists `block.road`.
- `map.open` stays exactly as it is: the chart is for orientation, a map app is for directions.
